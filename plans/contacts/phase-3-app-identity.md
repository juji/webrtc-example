# Phase 3 — App identity + installable PWA

## Files

`client/public/icon.svg`, `icon-maskable.svg` (new — SVG sources), `icon-192.png`, `icon-512.png`, `icon-maskable-512.png` (new — rendered PNGs), `client/public/manifest.json` (new), `client/public/sw.js` (new), `client/app/service-worker-registration.tsx` (new), `client/app/layout.tsx` (modified — metadata, viewport, mounts the registration component), `client/app/favicon.ico` (replaced).

## Why this phase exists before push notifications

Web Push (Phase 4) requires a registered service worker regardless of anything else — there is no way to receive a push event without one. And once a service worker exists, the app meets the core requirement for installability, so doing the manifest + icons at the same time (rather than as separate, later work) means Phase 4 lands on top of an app that already looks and feels like a real installed app, not a browser tab that happens to also get push. The user's framing was explicit about this: the icon/name work isn't cosmetic scope creep, it's what makes a push notification read as coming from "Primssg" rather than "localhost:3000" or a generic Chrome icon.

## Icon: one SVG source, rendered to the sizes a manifest needs

```svg
<!-- client/public/icon.svg -->
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 512 512">
  <rect width="512" height="512" rx="96" fill="#171717"/>
  <text x="256" y="326" font-family="Arial, Helvetica, sans-serif" font-size="300" font-weight="700" fill="#ffffff" text-anchor="middle">P</text>
</svg>
```

Dark square (`#171717`, matching the app's existing `--foreground`/dark-mode ink color from `globals.css`), rounded corners, bold white "P" — generated rather than sourced from an external asset, since no logo file existed and the request was simply "icon: P."

Rendered via `rsvg-convert` (already present on the machine, no new dependency needed — this is a one-time asset-generation step, not something the app runs at build/runtime) to the two sizes the [W3C manifest spec](https://developer.mozilla.org/en-US/docs/Web/Manifest/Reference/icons) expects at minimum: `icon-192.png` (192×192) and `icon-512.png` (512×512, also used as the browser tab/apple-touch icon via `layout.tsx`'s metadata).

**Maskable variant** (`icon-maskable.svg` → `icon-maskable-512.png`) is a second SVG, not a CSS/runtime transform of the first — Android/adaptive-icon-aware platforms crop a maskable icon to an arbitrary shape (circle, squircle, etc.), safely showing only the inner ~80% "safe zone." The regular icon's glyph fills close to the full square and would get clipped if reused as-is, so the maskable version repeats the same design with the "P" shrunk and recentered to survive that crop:

```svg
<!-- client/public/icon-maskable.svg — no rounded rect (mask handles the shape), smaller/recentered glyph -->
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 512 512">
  <rect width="512" height="512" fill="#171717"/>
  <text x="256" y="296" font-family="Arial, Helvetica, sans-serif" font-size="220" font-weight="700" fill="#ffffff" text-anchor="middle">P</text>
</svg>
```

## `manifest.json`

```json
{
  "name": "Primssg",
  "short_name": "Primssg",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#171717",
  "icons": [
    { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png", "purpose": "any" },
    { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png", "purpose": "any" },
    { "src": "/icon-maskable-512.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}
```

`display: standalone` is what makes an installed instance open without browser chrome (address bar, tabs) — the actual "feels like a real app" behavior, distinct from just having icons. `theme_color`/`background_color` are read by the OS for the splash screen and status-bar tinting on mobile.

## Wiring into `layout.tsx`

```tsx
export const metadata: Metadata = {
  title: "Primssg",
  description: "Post-quantum encrypted messaging over WebRTC",
  manifest: "/manifest.json",
  icons: { icon: "/icon-512.png", apple: "/icon-512.png" },
};

export const viewport = { themeColor: "#171717" };
```

Replaced the untouched create-next-app defaults (`title: "Create Next App"`, `description: "Generated by create next app"`) — these had never been updated since project scaffolding despite the app being a real, distinctly-purposed project by this point.

`favicon.ico` (`client/app/favicon.ico`) was also still the default Next.js icon; regenerated from the same `icon.svg` at 32×32 via `rsvg-convert` + `sips -s format ico` (both already on the machine, no new tooling).

## Service worker: minimal, install-only for now

```js
// client/public/sw.js
self.addEventListener("install", () => { self.skipWaiting(); });
self.addEventListener("activate", (event) => { event.waitUntil(self.clients.claim()); });
self.addEventListener("fetch", () => { /* no caching strategy yet — network passthrough */ });
```

Deliberately does nothing beyond the minimum Chrome/Android's installability heuristic checks for (a registered SW scope covering the page, with at least a `fetch` handler present). No caching strategy, no offline support — out of scope for this phase, and not needed for what push (Phase 4) will add, since `push`/`notificationclick` listeners are additive to this same file, not a redesign of it.

Registered from a root-mounted client component, matching the existing pattern of `SignalingConnection`/`MessageStatusListener` (both no-UI, `useEffect`-only components mounted in `layout.tsx`):

```tsx
// client/app/service-worker-registration.tsx
"use client";
export function ServiceWorkerRegistration() {
  useEffect(() => {
    if ("serviceWorker" in navigator) navigator.serviceWorker.register("/sw.js");
  }, []);
  return null;
}
```

## Explicitly not done in this phase

- No push subscription, no `push`/`notificationclick` handlers in `sw.js` — that's Phase 4, additive to this same file.
- No offline caching/asset precaching strategy.
- No "Add to Home Screen" / install-prompt UI — the manifest makes the app *installable* (browsers surface their own native install affordance), but no custom in-app install button was built.
- No apple-specific PWA meta tags beyond the `apple` icon entry (e.g. `apple-mobile-web-app-capable`) — iOS Safari's PWA support has more manual meta-tag requirements than Chrome/Android; not addressed here since push itself (Phase 4) has materially different, more limited support on iOS Safari regardless.

## Verification

1. `curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/manifest.json` (and the three icon PNGs, and `/sw.js`) all return 200.
2. Chrome DevTools → Application → Manifest: shows "Primssg", correct icons, no manifest errors/warnings.
3. Chrome DevTools → Application → Service Workers: shows `sw.js` registered and activated for the page's scope.
4. Browser tab shows the new "P" favicon instead of the default Next.js icon.
5. On a real device/Chrome desktop, the browser's install affordance (e.g. the install icon in the address bar) appears — confirms the manifest + SW combination actually satisfies installability, not just that the files exist.
6. `bunx tsc --noEmit` clean in `client/`.
